# Workspace records, schedules and drafts

- V56 adds monotonically increasing record/schedule revisions and company-scoped text snapshots. All record/schedule edit requests must send the revision originally loaded; row locks plus comparison reject stale edits with HTTP409. Previously opened clients need to reload. History begins with this release; photos are not versioned or restored by history.
- `/workspace/records/search` searches title/body/hospital with permission filtering before pagination (20 by default, max100). `/workspace/records/{id}` and `/history` authorize independently. The legacy full-list endpoint remains for overview and hospital history, without silently dropping records after500. Schedules have optional inclusive `from`/`to` dates and no1000-item cutoff; the schedule page fetches its selected day.
- Calendar export no longer drops records beyond500. Its inspection deadlines independently aggregate all completed nondeleted records, preserving imported baseline dates/overrides. Reconciliation still runs on changes and every10minutes.
- Schedule `PUT /workspace/schedules/{id}` preserves the ID and all record links. If active records are linked, changing hospital/target is refused. Date/time/title/type/body edits are supported. Editing is available to original author and admins.
- Work drafts stay in browser localStorage by user and record; new drafts share one slot per user. They expire after7days when read and are cleared after successful save. No image bytes or credentials are stored. Restore/discard is explicit; restored photo IDs are reauthorized and expired/missing staging photos are reported. Upload staging expiry remains24hours. Drafts do not sync between devices; private browsing/storage failures are reported. Refresh/tab-close and normal link navigation warn on unsaved changes; a browser history navigation can leave the page, with draft recovery available when returning.
- Verification:38 backend tests including an isolated local MariaDB fixture with520 records, unauthorized hospital filtering, pagination search, actual concurrent transactions (one success/one409), before/after history, schedule linkage preservation/hospital-change guard, date ranges; frontend production build. No test data inserted into production. No browser visual verification performed.
